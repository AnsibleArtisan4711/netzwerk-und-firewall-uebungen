## Aufgabe

### Aufgabe 1 – Aliase anlegen (Einheit 3.1)

Legen Sie die Aliase für Webserver, Web-Ports und Verwaltungsnetz an (Skript Schritt 1) und lesen Sie die Regel.

### Aufgabe 2 – Test (Einheit 3.3)

Rufen Sie Port 80, 8080 und 22 des Servers auf und erklären Sie das Ergebnis.

### Aufgabe 3 – Erweitern (Einheit 3.2)

Nehmen Sie Port 22 in den Port-Alias auf. Wird die Regel dafür geändert?

### Aufgabe 4 – Verkleinern (Einheit 3.2)

Entfernen Sie Port 8080 und prüfen Sie den Zugriff.

### Aufgabe 5 – Namenskonvention (Einheit 3.2)

Legen Sie eine Namenskonvention für Aliase fest (Präfix je Typ) und wenden Sie sie auf fünf Beispiele an.

### Aufgabe 6 – Fehlersuche (Einheit 3.4)

Ein Alias enthält `10.8.2.22` statt `10.8.2.2`. Wie fällt das auf?

## Hinweise

- Das Set `alias_verwaltung` nutzt `flags interval`, weil es ein Netz (`10.8.1.0/24`) statt einzelner Adressen enthält.
- Änderungen an einem Alias gelten sofort für alle Regeln, die ihn verwenden; ein Fehler wirkt daher breit.
- Die Zähler und Sets bleiben nur bis zum Neuladen erhalten (im Labor in `lab_down`).

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

1. Drei Sets (Hosts, Ports, Netz) und die Regel „LAN → Web“ verwenden nur Namen.
2. Port 80 und 8080: Antwort; Port 22: `keine Antwort`.
3. Nach `add element … { 22 }` antwortet Port 22; die Regel blieb unverändert.
4. Nach `delete element … { 8080 }`: Port 8080 keine Antwort, Port 80 Antwort.
5. Beispiel: `h_web`, `n_lan`, `p_web`, `h_dns`, `p_mail`.
6. `nft list set …` zeigt `elements = { 10.8.2.22 }`: die Adresse fehlt, Zugriff scheitert.

**Kontrollfragen (Antwortskizzen):**

1. Eine Änderung an einer Stelle wirkt in allen Regeln; Regeln bleiben lesbar.
2. Hosts, Netze und Ports (weitere Typen nicht bestätigt).
3. Die Regel verweist nur auf den Namen; der Inhalt wird zur Laufzeit gelesen.
4. Zyklen vermeiden, Namen eindeutig halten; Verhalten in OPNsense nicht bestätigt.

</details>
