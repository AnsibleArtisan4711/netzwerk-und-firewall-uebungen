## Lernziele

Nach dieser Übung kannst du

- zwei Subnetze bidirektional über WireGuard routen

## Voraussetzungen

- Modul 4 (`wg0` läuft auf beiden VMs); die Dummy-Interfaces sind angelegt (nach einem Neustart `lab-dummy.sh` ausführen)

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Site-to-Site** | zwei Gateways verbinden zwei Standortnetze; hier `192.168.10.0/24` ↔ `192.168.20.0/24` |
| **`wg syncconf`** | gleicht eine laufende Schnittstelle mit einer Konfiguration ab, ohne sie neu zu starten |
| **`wg-quick strip`** | gibt die Konfiguration ohne `wg-quick`-eigene Zeilen (`Address`, `PostUp` …) aus |
| **Routenkonflikt** | zwei Tunnel setzen Routen in dasselbe Zielnetz |
| **Endpoint** | Gegenstelle mit Adresse und Port; der Server lernt ihn aus dem ersten Paket des Clients |

## Laborumgebung

| Was | Rolle in Modul 05 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |
| Zustand | WireGuard läuft auf beiden VMs (Modul 4); `lab-dummy.sh` wurde ausgeführt |

## Aufgabe

### Aufgabe 1 – Routing für Site B bekanntgeben (Einheit 5.1, Einheit 5.2)

Bearbeiten Sie auf `VM 1` (Server) den `[Peer]`-Eintrag für VM 2. Ändern Sie `AllowedIPs = 10.8.0.100/32, 192.168.20.0/24`. Übernehmen Sie die Änderung mit `wg-quick down wg0` und `wg-quick up wg0`. Prüfen Sie mit `ip route show dev wg0`, dass die Route `192.168.20.0/24` vorhanden ist.

### Aufgabe 2 – Verhalten von `wg syncconf` beobachten (Einheit 5.2)

Entfernen Sie `192.168.20.0/24` aus den `AllowedIPs`, laden Sie mit `wg syncconf wg0 <(wg-quick strip wg0)` neu (in `bash`) und prüfen Sie `wg show wg0 allowed-ips` und `ip route show dev wg0`. Tragen Sie den Eintrag wieder ein, laden Sie erneut mit `wg syncconf` und prüfen Sie, ob die Route `192.168.20.0/24` wieder erscheint (erwartet: nein, weil `wg-quick` die Routen beim Start setzt und `wg syncconf` nur die Schnittstelle abgleicht; nicht bestätigt). Stellen Sie den Zustand mit `wg-quick down wg0` und `wg-quick up wg0` wieder her.

**Hinweis/Ergänzung der Ausarbeitung (Befund der Testumgebung):** `wg syncconf` ändert die Routen nicht – weder in die eine noch in die andere Richtung. Beim Entfernen von `192.168.20.0/24` aus den `AllowedIPs` blieb die Route stehen, und eine von Hand gelöschte Route kam beim erneuten Eintragen und `wg syncconf` nicht zurück. Die Erwartung „Route wieder erscheint: nein“ des Lehrplans trifft damit zu, aber sie gilt auch für das Entfernen. Die Befehle in einer Root-Shell (`sudo -i`) ausführen, weil die Prozess-Ersetzung `<(…)` sonst als normaler Benutzer läuft und `/etc/wireguard` nicht lesen kann.

### Aufgabe 3 – Ping-Test zwischen LANs (Einheit 5.3)

Pingen Sie von `VM 1` mit `ping -c 3 -I 192.168.10.1 192.168.20.1` und von `VM 2` mit `ping -c 3 -I 192.168.20.1 192.168.10.1` (die Quelladresse stammt jeweils aus dem eigenen Site-Netz). Beide Pings müssen über den Tunnel (`10.8.0.x`) laufen. Führen Sie parallel auf `VM 2` den Befehl `tcpdump -i wg0 -n icmp` aus, um den Tunnel-Traffic nachzuweisen.

**Hinweis/Ergänzung der Ausarbeitung (Befund der Testumgebung):** Pingt `VM 1` als Erstes, schlägt der Test mit 100 % Paketverlust fehl: Der Server kennt den Endpoint des Clients erst, wenn der Client ein Paket geschickt hat. Zuerst von `VM 2` pingen (oder `PersistentKeepalive = 25` im Client-Peer setzen), dann von `VM 1`.

### Aufgabe 4 – Rückbau (Einheit 5.1)

Stoppen Sie am Ende des Moduls auf beiden Systemen WireGuard mit `wg-quick down wg0`, um Routenkonflikte mit OpenVPN (ab Modul 6, beide setzen Routen in die Netze `192.168.10.0/24` und `192.168.20.0/24`) zu vermeiden.

## Hinweise

- `wg-quick down` / `up` unterbricht den Tunnel kurz, `wg syncconf` nicht – dafür bleiben Routen unverändert.
- Die Pings der Aufgabe 3 benutzen Quelladressen aus den Site-Netzen (`-I`). Damit werden `AllowedIPs` auf beiden Seiten tatsächlich geprüft; ein Ping von der Tunneladresse würde das nicht.
- Beide Gateways pingen sich mit eigenen Adressen: dafür ist Forwarding nicht nötig. Für Rechner **hinter** den Gateways schon (siehe Frage 3 und Modul 11).
- Zum Schluss WireGuard stoppen, sonst stört der Routenkonflikt die OpenVPN-Module.

## Kontrollfragen

1. Warum muss das Subnetz von Site B in den `AllowedIPs` auf Site A zwingend eingetragen werden?
2. Welchen Vorteil bietet der Befehl `wg syncconf` gegenüber einem Neustart des Interfaces mit `wg-quick down/up`, und was setzt er (laut Aufgabe 2) nicht um?
3. Warum reicht die WireGuard-Konfiguration allein nicht aus, wenn das IP-Forwarding im Kernel deaktiviert ist?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Routing für Site B bekanntgeben).** VM 1, im `[Peer]`-Block:

```ini
AllowedIPs = 10.8.0.100/32, 192.168.20.0/24
```

```bash
wg-quick down wg0 && wg-quick up wg0
ip route show dev wg0
```

Zielzustand (Testumgebung, `beispiele/m05.txt`): `10.8.0.0/24 proto kernel scope link src 10.8.0.1` und `192.168.20.0/24 scope link`.

**Aufgabe 2 (Verhalten von `wg syncconf` beobachten).**

```bash
# Eintrag 192.168.20.0/24 aus AllowedIPs entfernen
wg syncconf wg0 <(wg-quick strip wg0)
wg show wg0 allowed-ips      # nur 10.8.0.100/32
ip route show dev wg0        # Route 192.168.20.0/24 steht noch
# Route von Hand löschen und Eintrag wieder ergänzen
ip route del 192.168.20.0/24 dev wg0
wg syncconf wg0 <(wg-quick strip wg0)
wg show wg0 allowed-ips      # 10.8.0.100/32 192.168.20.0/24
ip route show dev wg0        # Route ist NICHT zurück
wg-quick down wg0 && wg-quick up wg0   # Zustand wieder herstellen
```

Die Ausgaben stammen aus der Testumgebung (`beispiele/m05.txt`). Der Lehrplan erwartet „Route kommt nicht wieder“; bestätigt, aber zusätzlich: auch beim Entfernen wird die Route nicht gelöscht.

**Aufgabe 3 (Ping-Test zwischen LANs).** Von `VM 2` (zuerst, siehe Hinweis):

```bash
ping -c 3 -I 192.168.20.1 192.168.10.1
sudo tcpdump -i wg0 -n icmp
```

Dann von `VM 1`: `ping -c 3 -I 192.168.10.1 192.168.20.1`. Erwartung: 0 % Verlust, in `tcpdump` Pakete `192.168.10.1 > 192.168.20.1` und die Antworten (Testumgebung). Pingt `VM 1` als Erstes nach einem Neustart des Interfaces, gingen in der Testumgebung alle drei Pings verloren.

**Aufgabe 4 (Rückbau).**

```bash
wg-quick down wg0      # auf beiden VMs
ip route               # keine Route mehr über wg0
```

Zielzustand: kein `wg0`, keine Routen der Site-Netze über den Tunnel.

**Fragen.** (1) Der Server nimmt Pakete von einem Peer nur an, wenn die Quelladresse in dessen `AllowedIPs` liegt, und schickt Pakete nur dann an einen Peer, wenn das Ziel in dessen `AllowedIPs` liegt. Ohne `192.168.20.0/24` würden Antworten nach Site B nicht in den Tunnel zu VM 2 gelangen und Pakete von Site B am Server verworfen. (2) `wg syncconf` ändert die Schnittstelle im Betrieb: bestehende Verbindungen und Handshakes bleiben, es gibt keine Unterbrechung. Es setzt weder Adressen noch Routen (in der Testumgebung bestätigt: Routen bleiben unverändert und kommen nicht zurück). (3) Das Forwarding betrifft Pakete, die weder von noch an das Gateway selbst gehen, also den Verkehr von Rechnern hinter den Gateways. Ohne `ip_forward` würde der Kernel solche Pakete verwerfen. Die Pings dieses Moduls zwischen den Gateway-Adressen kommen auch ohne Forwarding aus (Fachwissen, mit `ip_forward=0` nicht getestet).

</details>
