## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Site-to-Site mit OpenVPN** | Server und Client verbinden je ein Standortnetz; Client wird zum Gateway von Site B |
| **`route` + `iroute`** | Kernel-Route am Server plus interne Route für das Client-Subnetz |
| **`ip route get`** | zeigt, welchen Weg der Kernel für ein Ziel wählt |
| **Reverse Path** | Pakete werden nur akzeptiert, wenn die Quelladresse zum Client passt (`iroute`) |
| **`verb`** | Ausführlichkeit des OpenVPN-Logs (0–11) |

## Laborumgebung

| Was | Rolle in Modul 10 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |
| CCD | `client1` mit `ifconfig-push 10.9.0.50` und `iroute` |
| Dummy | `192.168.20.1/24` auf VM 2 als Site B |

## Aufgabe

### Aufgabe 1 – Kernel-Route am Server (Einheit 10.3)

Ergänzen Sie die `server.conf` auf `VM 1` um die Direktive `route 192.168.20.0 255.255.255.0`.

### Aufgabe 2 – Interne Route (iroute) am Server (Einheit 10.2)

Ergänzen Sie die CCD-Datei `/etc/openvpn/server/ccd/client1` um die Direktive `iroute 192.168.20.0 255.255.255.0`. Starten Sie den OpenVPN-Server neu.

### Aufgabe 3 – Bidirektionaler Ping-Test (Einheit 10.1, Einheit 10.3)

Starten Sie den Server (`systemctl start openvpn-server@server`, falls nötig) und verbinden Sie `VM 2` (`sudo openvpn --config /etc/openvpn/client/client1.ovpn`). Prüfen Sie auf `VM 1` mit `ip route get 192.168.20.1`, dass der Weg über `tun0` führt. Pingen Sie von `VM 1` auf das Dummy-Interface von Site B (`ping -c 3 192.168.20.1`) und von `VM 2` in einem zweiten Terminal mit `ping -c 3 -I 192.168.20.1 192.168.10.1`.

**Hinweis/Ergänzung der Ausarbeitung (Befund der Testumgebung):** Fehlt `iroute`, ging der Ping verloren. Die Meldung `MULTI: bad source address from client [192.168.20.1], packet dropped` erschien in der Testumgebung erst bei `verb 6` oder höher, bei `verb 3` (Voreinstellung der Tests) nicht; der Fehler zeigt sich dort nur als Zeitüberschreitung des Pings. Zum Suchen den Server testweise mit `--verb 6` starten.

### Aufgabe 4 – Rückbau / Trennung (Einheit 10.1)

Beenden Sie den OpenVPN-Client-Prozess auf `VM 2` (Strg+C) und den Dienst auf `VM 1` mit `systemctl disable --now openvpn-server@server`. Spätere Module starten den Dienst bei Bedarf selbst.

## Hinweise

- In der Testumgebung wurde die Variante ohne `iroute` zuerst gemessen (100 % Verlust), danach mit `iroute` (0 % Verlust).
- VM 2 braucht für Pings aus Site B die Quelladresse `-I 192.168.20.1`; ohne `-I` wird die Tunneladresse als Quelle benutzt und der Test prüft das Site-Netz nicht.
- Der Dienst wird am Ende deaktiviert (`disable --now`), damit er bei einem Neustart nicht gleichzeitig mit WireGuard läuft.
- Schließe nach dem Test das Terminalfenster mit dem Client mit Strg+C.

## Kontrollfragen

1. Erklären Sie das Zusammenspiel zwischen `route` (in der server.conf) und `iroute` (in der CCD-Datei) bei einem Site-to-Site Setup in OpenVPN.
2. Warum ist bei Site-to-Site-Verbindungen das IP-Forwarding auf beiden Seiten zwingend erforderlich?
3. Welcher Fehler tritt im Ping-Test auf, wenn das `iroute` fehlt, aber das `route` gesetzt ist?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Kernel-Route am Server).**

```text
# /etc/openvpn/server/server.conf  (VM 1)
route 192.168.20.0 255.255.255.0
```

Zielzustand: nach dem Start `ip route` mit `192.168.20.0/24 via … dev tun0` (Testumgebung: `192.168.20.0/24 via 10.9.0.2 dev tun0`, siehe `beispiele/m10.txt`).

**Aufgabe 2 (Interne Route (iroute) am Server).**

```text
# /etc/openvpn/server/ccd/client1  (VM 1)
ifconfig-push 10.9.0.50 255.255.255.0
iroute 192.168.20.0 255.255.255.0
```

Server neu starten. Im Log erscheint `MULTI: Learn: 192.168.20.0/24 -> client1/…` (Testumgebung).

**Aufgabe 3 (Bidirektionaler Ping-Test).**

```bash
ip route get 192.168.20.1       # 192.168.20.1 via … dev tun0
ping -c 3 192.168.20.1          # VM 1 -> Site B
ping -c 3 -I 192.168.20.1 192.168.10.1     # VM 2 -> Site A
```

Beobachtung in der Testumgebung (`beispiele/m10.txt`): ohne `iroute` 100 % Paketverlust in beiden Richtungen; mit `iroute` 0 % Verlust in beiden Richtungen.

**Aufgabe 4 (Rückbau / Trennung).**

```bash
# VM 2: Strg+C im Client-Terminal
sudo systemctl disable --now openvpn-server@server    # VM 1
```

`systemctl` wurde in der Testumgebung **nicht** ausgeführt; der Prozess wurde beendet.

**Fragen.** (1) `route` (Server-Konfiguration) setzt die Kernel-Route für `192.168.20.0/24` auf `tun0`, damit Pakete überhaupt an OpenVPN gelangen. `iroute` (CCD-Datei des Clients) sagt dem OpenVPN-Prozess, hinter welchem Client dieses Netz liegt, damit er das Paket an den richtigen Client schickt und Pakete aus diesem Netz akzeptiert. Beides ist nötig (bestätigt: nur `route` genügt nicht). (2) Forwarding wird gebraucht, wenn ein Gateway Pakete für Rechner **hinter** dem Gateway weiterreicht. Die Pings dieses Moduls laufen zwischen den Gateways selbst; ob sie ohne Forwarding funktionieren, wurde nicht getestet (Forwarding war aktiviert). Für Endgeräte der Standorte ist es zwingend (Fachwissen). (3) Der Ping hat 100 % Paketverlust (Zeitüberschreitung); in der Testumgebung zeigte der Server die Meldung `MULTI: bad source address from client …, packet dropped` nur bei `verb 6` oder höher.

</details>

## Erweiterungen

- Beobachte mit `verb 6` das Auftauchen von `bad source address` ohne `iroute`.
- Setze die `route`-Direktive um auf `route 192.168.20.0 255.255.255.0 10.9.0.50` (zeigt die Adresse des Clients) und prüfe die Ausgabe von `ip route get`.
