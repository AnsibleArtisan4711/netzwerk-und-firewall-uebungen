Versionen der Testumgebung: Ubuntu 24.04 im Cloud-Container mit Namensräumen statt VMs; wireguard-tools 1.0.20210914, wireguard-go v0.0.20230223 (Userspace, kein Kernelmodul), OpenVPN 2.6.19 (OpenSSL 3.0.13), EasyRSA 3.1.7, nftables 1.0.9, tcpdump 4.99.4, iproute2 6.1.0. Ausgaben im Ordner `beispiele/` stammen aus der Testumgebung; Adaptername (`eth0`), Adressen und Meldungen der VMs können abweichen.

## Lernziele

Nach dieser Übung kannst du

- IPv4-Forwarding unter Linux temporär und persistent aktivieren
- virtuelle Dummy-Schnittstellen anlegen

## Voraussetzungen

- Beide VMs sind mit Debian 12 installiert (Prüfpunkt `Basis`) und am `Default Switch` mit Internetzugang (DHCP). Alle Befehle mit `sudo` als Benutzer `labadmin`.

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **`ip_forward`** | Kernel-Schalter `net.ipv4.ip_forward`: erlaubt dem Linux-Rechner, Pakete zwischen Schnittstellen weiterzuleiten |
| **`sysctl`** | Werkzeug zum Lesen und Setzen von Kernelparametern (`-w` temporär, `sysctl.conf` persistent) |
| **Dummy-Interface** | virtuelle Schnittstelle ohne Gegenstelle, hier als simuliertes LAN eines Standorts |
| **Privater vSwitch** | Hyper-V-Switch ohne Host-Adapter und ohne Internet |
| **Prüfpunkt** | Hyper-V-Checkpoint einer VM |

## Laborumgebung

| Was | Rolle in Modul 02 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |
| `lab-dummy.sh` | Skript aus dem Lehrplan; legt `dummy0` an |
| `testlabor-namespaces.sh` | Hilfsmittel der Ausarbeitung für die Testumgebung (nicht Teil des Lehrplans) |

## Aufgabe

### Aufgabe 1 – Paketinstallation (Internet-Phase) (Einheit 2.1)

Prüfen Sie auf beiden VMs mit `ip -br a`, dass der Adapter eine Adresse vom `Default Switch` hat. Installieren Sie die Pakete: `sudo apt update && sudo apt install -y wireguard openvpn easy-rsa nftables tcpdump`. Ändern Sie danach in den Hyper-V-Einstellungen den Adapter beider VMs auf den isolierten Switch `VPN-Lab-WAN`.

### Aufgabe 2 – Statische IPs vergeben (Einheit 2.2)

Ermitteln Sie den Adapternamen mit `ip -br a`. Tragen Sie in `/etc/network/interfaces` für diesen Adapter (hier `eth0`) statt `dhcp` die Zeilen `iface eth0 inet static` und `address 10.0.0.1/24` ein (VM 2: `address 10.0.0.100/24`, jeweils ohne Gateway) und laden Sie die Konfiguration mit `sudo systemctl restart networking` (Datei und Verfahren für Debian 12 nicht bestätigt). Testen Sie die Erreichbarkeit mit `ping -c 3` zwischen den VMs.

### Aufgabe 3 – Routing aktivieren (Einheit 2.2)

Aktivieren Sie auf `VM 1` und `VM 2` das IP-Forwarding zuerst temporär (`sudo sysctl -w net.ipv4.ip_forward=1`) und prüfen Sie es mit `sysctl net.ipv4.ip_forward`. Aktivieren Sie es danach persistent: Entfernen Sie in `/etc/sysctl.conf` das Kommentarzeichen vor `net.ipv4.ip_forward=1` (oder fügen Sie die Zeile hinzu) und wenden Sie die Datei mit `sudo sysctl -p` an. Das Ergebnis nach einem Neustart ist im Prüfpunkt der Aufgabe 5 zu bestätigen.

### Aufgabe 4 – Dummy-Interfaces anlegen (Einheit 2.3)

Legen Sie auf `VM 1` das Skript `/usr/local/sbin/lab-dummy.sh` (ausführbar) mit diesem Inhalt an und führen Sie es mit `sudo` aus; auf `VM 2` verwenden Sie `192.168.20.1/24`:
```sh
#!/bin/sh
modprobe dummy
ip link show dummy0 >/dev/null 2>&1 || ip link add dummy0 type dummy
ip addr replace 192.168.10.1/24 dev dummy0
ip link set dummy0 up
```
Prüfen Sie mit `ip -br a show dummy0`. Die Schnittstelle bleibt nach einem Neustart nicht erhalten; das Skript wird dann erneut ausgeführt.

**Hinweis/Ergänzung der Ausarbeitung:** Das Kernelmodul `dummy` stand in der Testumgebung nicht zur Verfügung (Cloud-Container ohne Modul); dort trug `lo` die Adresse `192.168.10.1/24` bzw. `192.168.20.1/24`. Das Skript wurde deshalb **nicht ausgeführt**. Auf einer VM mit Debian-Kernel prüfen, ob `modprobe dummy` funktioniert.

### Aufgabe 5 – Prüfpunkt (Einheit 2.2, Einheit 2.3)

Starten Sie beide VMs neu, prüfen Sie `sysctl net.ipv4.ip_forward` und führen Sie `lab-dummy.sh` aus. Erstellen Sie danach auf beiden VMs den Hyper-V-Prüfpunkt `M2-fertig`.

## Hinweise

- Aufgabe 2 ändert die Netzwerkkonfiguration; bei einem Fehler ist die Hyper-V-Konsole der Ersatzzugang (Hyper-V-Konsole statt SSH).
- Der Adaptername `eth0` ist nicht bestätigt; erst `ip -br a`, dann ändern.
- Nach dem Umstellen auf `VPN-Lab-WAN` gibt es kein Internet mehr; Pakete müssen vorher installiert sein.
- Das Skript `lab-dummy.sh` ist idempotent geschrieben (zweiter Lauf ändert nichts), `ip addr replace` ersetzt eine vorhandene Adresse.

## Kontrollfragen

1. Welcher Parameter in der `sysctl.conf` ist zwingend nötig, damit ein Linux-Server als VPN-Router fungieren kann?
2. Welchem Zweck dient das Modul `dummy` in unserem spezifischen isolierten Labor-Setup?
3. Warum müssen die Hyper-V VMs nach Aufgabe 1 zwingend in einen rein privaten virtuellen Switch verschoben werden?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Paketinstallation (Internet-Phase)).** Auf beiden VMs:

```bash
ip -br a
sudo apt update && sudo apt install -y wireguard openvpn easy-rsa nftables tcpdump
```

Danach in Hyper-V den Adapter von `Default Switch` auf `VPN-Lab-WAN` umstellen. Zielzustand: Pakete installiert (`dpkg -l wireguard openvpn easy-rsa nftables tcpdump`), danach kein Internet mehr. **Nicht ausgeführt**: weder `apt` noch die Hyper-V-Umstellung.

**Aufgabe 2 (Statische IPs vergeben).** VM 1 (`/etc/network/interfaces`, Adapter `eth0` angenommen):

```text
auto eth0
iface eth0 inet static
    address 10.0.0.1/24
```

VM 2: `address 10.0.0.100/24`. Dann `sudo systemctl restart networking` und `ping -c 3 10.0.0.100` bzw. `10.0.0.1`. Debian 12 mit `/etc/network/interfaces` und `networking.service` ist **nicht bestätigt** (laut Lehrplan); in der Testumgebung wurden die Adressen mit `ip addr add` gesetzt, die Ping-Verbindung `10.0.0.1` ↔ `10.0.0.100` war erfolgreich.

**Aufgabe 3 (Routing aktivieren).**

```bash
sudo sysctl -w net.ipv4.ip_forward=1
sysctl net.ipv4.ip_forward          # net.ipv4.ip_forward = 1
echo 'net.ipv4.ip_forward=1' | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

Zielzustand: Ausgabe `net.ipv4.ip_forward = 1`. Der temporäre Befehl wurde in der Testumgebung ausgeführt (im Namespace); die persistente Variante und `sysctl -p` wurden **nicht** ausgeführt. Das Ergebnis nach einem Neustart ist im Prüfpunkt (Aufgabe 5) zu bestätigen.

**Aufgabe 4 (Dummy-Interfaces anlegen).** Inhalt und Aufruf wie im Lehrplan (Skript im Kursordner: `lab-dummy.sh`):

```bash
sudo install -m 755 lab-dummy.sh /usr/local/sbin/lab-dummy.sh
sudo /usr/local/sbin/lab-dummy.sh
ip -br a show dummy0        # dummy0  UNKNOWN  192.168.10.1/24
```

VM 2: Adresse im Skript auf `192.168.20.1/24` ändern. **Nicht ausgeführt**: In der Testumgebung gab es kein `dummy`-Modul; dort lag die Adresse auf `lo`. Die Zeile `modprobe dummy` benötigt root; ob das Modul im Debian-Kernel vorhanden ist, ist offen.

**Aufgabe 5 (Prüfpunkt).** Nach `sudo reboot` auf beiden VMs:

```bash
sysctl net.ipv4.ip_forward           # Erwartung: 1 (persistent gesetzt)
sudo /usr/local/sbin/lab-dummy.sh    # dummy0 ist weg und wird neu angelegt
```

Danach Hyper-V-Prüfpunkt `M2-fertig` auf beiden VMs. **Nicht ausgeführt.**

**Fragen.** (1) `net.ipv4.ip_forward=1`. Ohne ihn verwirft der Kernel Pakete, die nicht für ihn selbst bestimmt sind, statt sie weiterzuleiten. (2) Es erzeugt ohne zusätzliche Hardware ein lokales Netz je Standort, hier `192.168.10.0/24` bzw. `192.168.20.0/24`, mit dem Site-to-Site-Routing ausprobiert werden kann. (3) Damit die Labor-VMs keine Verbindung zu Heim- oder Firmennetz haben: Routen und Dienste (z. B. DHCP, Namensauflösung, öffentliche Adressen) könnten das Labor stören und umgekehrt könnte der Labor-Verkehr das echte Netz erreichen. Der Lehrplan fordert die Isolation (privater Switch). Ausserdem wäre sonst nicht sichergestellt, dass der Tunnel den Weg nimmt, den die Aufgaben testen.

</details>

## Erweiterungen

- Richte `lab-dummy.sh` als Dienst ein, der beim Start läuft (z. B. systemd-Unit). Beachte, dass WireGuard und OpenVPN dort **nicht** automatisch starten sollen.
- Lies `sysctl net.ipv4.conf.all.forwarding` und `net.ipv4.conf.default.forwarding` und erkläre den Unterschied zu `net.ipv4.ip_forward`.
