## Lernziele

Nach dieser Übung kannst du

- eine funktionale `server.conf` für OpenVPN erstellen
- den OpenVPN-Dienst als Systemd-Service verwalten

## Voraussetzungen

- Modul 6 (CA, Server-Cert, Server-Key, DH-Parameter vorhanden)

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **`server.conf`** | Konfiguration des OpenVPN-Servers, Verzeichnis `/etc/openvpn/server/` |
| **`topology subnet`** | Clients erhalten Adressen aus einem gemeinsamen Subnetz (statt Punkt-zu-Punkt-`net30`) |
| **`tls-crypt`** | verschlüsselt und authentifiziert die TLS-Kontrollpakete mit einem statischen Schlüssel |
| **`tls-auth`** | nur Authentifizierung (HMAC) der Kontrollpakete |
| **`openvpn-server@server`** | systemd-Instanz; `server` steht für `server.conf` |
| **`ss -uln`** | lauschende UDP-Sockets |

## Laborumgebung

| Was | Rolle in Modul 07 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |
| Dateien | `ca.crt`, `server.crt`, `server.key`, `dh.pem`, `ta.key` in `/etc/openvpn/server/` |

## Aufgabe

### Aufgabe 1 – Zertifikate kopieren (Einheit 7.2)

Kopieren Sie auf `VM 1` aus `/etc/openvpn/easy-rsa` die Dateien `pki/ca.crt`, `pki/issued/server.crt`, `pki/private/server.key` und `pki/dh.pem` nach `/etc/openvpn/server/`. Generieren Sie zusätzlich einen statischen TLS-Schlüssel: `openvpn --genkey secret /etc/openvpn/server/ta.key`.

### Aufgabe 2 – Server-Konfiguration anlegen (Einheit 7.1, Einheit 7.2)

Erstellen Sie `/etc/openvpn/server/server.conf`. Parameter: `port 1194`, `proto udp`, `dev tun`, `topology subnet`, `server 10.9.0.0 255.255.255.0`, `tls-crypt ta.key`, `push "route 192.168.10.0 255.255.255.0"`. Referenzieren Sie die Zertifikate mit `ca ca.crt`, `cert server.crt`, `key server.key` und `dh dh.pem` (relative Pfade, da der Dienst im Verzeichnis `/etc/openvpn/server` startet; nicht bestätigt).

**Hinweis/Ergänzung der Ausarbeitung:** Relative Pfade funktionieren, wenn der Prozess im Verzeichnis der Konfiguration läuft. In der Testumgebung wurde dazu `openvpn --cd /pfad --config server.conf` benutzt; das Arbeitsverzeichnis, das `openvpn-server@server` unter Debian setzt, wurde **nicht** geprüft.

### Aufgabe 3 – Dienst starten (Einheit 7.3)

Aktivieren und starten Sie den Dienst mit `systemctl enable --now openvpn-server@server`. Prüfen Sie ihn mit `systemctl status openvpn-server@server` und `journalctl -u openvpn-server@server -n 20`, starten Sie ihn mit `systemctl restart openvpn-server@server` neu und stellen Sie sicher, dass er danach läuft.

### Aufgabe 4 – Verifikation (Einheit 7.3)

Prüfen Sie mit `ss -uln`, ob Port 1194 (UDP) lauscht. Prüfen Sie mit `ip a`, ob das `tun0` Interface existiert und die IP `10.9.0.1` hat.

## Hinweise

- `ta.key` ist ein geheimer Schlüssel; Rechte 600, nicht in ein Repository.
- In der Testumgebung gab es kein systemd; der Server lief als `openvpn --daemon`. `systemctl`-Befehle wurden **nicht** ausgeführt.
- Der Befehl zum Erzeugen des Schlüssels lautet bei OpenVPN 2.6 `openvpn --genkey secret <Datei>` (bestätigt: Version 2.6.19).
- `tls-crypt` (Server) und `<tls-crypt>` (Client) müssen denselben Schlüssel enthalten.

## Kontrollfragen

1. Was bewirkt die Direktive `topology subnet` im Vergleich zur älteren `topology net30`?
2. Welchen Schutzmechanismus bietet die Option `tls-crypt` gegenüber der älteren `tls-auth` Direktive?
3. Warum verwendet OpenVPN standardmäßig UDP statt TCP als Transportprotokoll?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Zertifikate kopieren).**

```bash
cd /etc/openvpn/easy-rsa
cp pki/ca.crt pki/issued/server.crt pki/private/server.key pki/dh.pem /etc/openvpn/server/
openvpn --genkey secret /etc/openvpn/server/ta.key
chmod 600 /etc/openvpn/server/server.key /etc/openvpn/server/ta.key
```

In der Testumgebung ausgeführt; die erste Zeile von `ta.key` ist ein Kommentar (`#`).

**Aufgabe 2 (Server-Konfiguration anlegen).** `/etc/openvpn/server/server.conf`:

```text
port 1194
proto udp
dev tun
topology subnet
server 10.9.0.0 255.255.255.0
tls-crypt ta.key
push "route 192.168.10.0 255.255.255.0"
ca ca.crt
cert server.crt
key server.key
dh dh.pem
```

**Aufgabe 3 (Dienst starten).**

```bash
systemctl enable --now openvpn-server@server
systemctl status openvpn-server@server
journalctl -u openvpn-server@server -n 20
systemctl restart openvpn-server@server
systemctl is-active openvpn-server@server
```

**Nicht ausgeführt** (kein systemd in der Testumgebung). Zielzustand: Status `active (running)`, im Journal die Zeile `Initialization Sequence Completed`. Der Server startete in der Testumgebung mit `openvpn --cd … --config server.conf --daemon`; die Ausgabe `Initialization Sequence Completed` stand im Log.

**Aufgabe 4 (Verifikation).**

```bash
ss -uln | grep 1194       # UNCONN 0 0 0.0.0.0:1194
ip -br a show tun0        # tun0 UNKNOWN 10.9.0.1/24
```

Erwartung bestätigt in der Testumgebung (`beispiele/m07.txt`).

**Fragen.** (1) Bei `topology subnet` bekommen alle Clients Adressen aus dem Subnetz des Servers (`10.9.0.0/24`), wie in einem normalen LAN. `net30` vergibt jedem Client ein eigenes /30 und verbraucht vier Adressen je Client; es ist die ältere Punkt-zu-Punkt-Variante. (2) `tls-crypt` verschlüsselt zusätzlich zur Authentifizierung die TLS-Kontrollpakete; ein Angreifer ohne Schlüssel erkennt den Handshake nicht und kann ihn nicht gezielt stören. `tls-auth` sichert die Pakete nur per HMAC. (Aussage: Fachwissen des Verfassers, nicht gegen eine Quelle geprüft; das Verwerfen von Paketen mit falschem Schlüssel wurde in Modul 12 beobachtet: `tls-crypt unwrap error: packet authentication failed`.) (3) UDP hat keinen Wiederholmechanismus; die tunnelinterne Anwendung (z. B. TCP) übernimmt die Zuverlässigkeit. Würde OpenVPN selbst über TCP tunneln, würden zwei Wiederholmechanismen gegeneinander arbeiten („TCP over TCP“). (Aussage: Fachwissen des Verfassers, nicht gegen eine Quelle geprüft.)

</details>
