## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **`nftables`** | Paketfilter-Framework des Linux-Kernels; Tabellen, Ketten, Regeln |
| **Hook `input`/`forward`/`postrouting`** | Stellen im Paketweg: an das Gateway, durch das Gateway, nach dem Routing |
| **Policy** | Standardentscheidung einer Kette (`drop` oder `accept`) |
| **`ct state`** | Verbindungszustand (`established`, `related`, `new`, `invalid`) |
| **Masquerading** | Quelladresse ersetzen durch die Adresse der ausgehenden Schnittstelle |
| **Network Namespace** | getrennter Netzwerkstack; hier simuliert er den Rechner `lan-a` |
| **Prüfpunkt `M11-Start`** | Hyper-V-Prüfpunkt vor dem Sperren |

## Aufgabe

### Aufgabe 1 – Prüfpunkt und LAN-Host simulieren (Einheit 11.1)

Erstellen Sie auf `VM 1` den Hyper-V-Prüfpunkt `M11-Start` und stoppen Sie alle Tunnel (`wg-quick down wg0`, `systemctl stop openvpn-server@server`). Weiterleitung lässt sich mit den bisherigen Dummy-Interfaces nicht zeigen, weil die LAN-Adresse auf dem Gateway selbst liegt. Legen Sie daher das Skript `/usr/local/sbin/lab-lan-a.sh` an (ausführbar) und führen Sie es mit `sudo` aus; es ersetzt `dummy0` durch einen simulierten Rechner `lan-a` (`192.168.10.10`) in einem Netzwerk-Namespace:
```sh
#!/bin/sh
ip addr flush dev dummy0
ip netns add lan-a
ip link add veth-gw type veth peer name veth-host
ip link set veth-host netns lan-a
ip addr add 192.168.10.1/24 dev veth-gw
ip link set veth-gw up
ip netns exec lan-a ip addr add 192.168.10.10/24 dev veth-host
ip netns exec lan-a ip link set veth-host up
ip netns exec lan-a ip link set lo up
ip netns exec lan-a ip route add default via 192.168.10.1
```
Prüfen Sie mit `ping -c 2 192.168.10.10`. Nach einem Neustart wird das Skript erneut ausgeführt (zuvor `ip netns del lan-a`, falls der Namespace noch existiert). Das Skript wurde nicht ausgeführt (nicht bestätigt).

**Hinweis/Ergänzung der Ausarbeitung:** In der Testumgebung gab es kein `dummy0`; die Befehle des Skripts wurden einzeln von außen mit `ip -n` ausgeführt, das Skript selbst wurde nicht gestartet.

### Aufgabe 2 – Basis-Regelwerk anlegen (Einheit 11.1, Einheit 11.3)

Erstellen Sie auf `VM 1` die Datei `/etc/nftables.conf` mit folgendem Inhalt. Die `input`-Kette verwirft standardmäßig alles (Policy `drop`), erlaubt aber `lo`, bestehende Verbindungen, Ping, `SSH (TCP 22)`, `WireGuard (UDP 51820)` und `OpenVPN (UDP 1194)`. Die `forward`-Kette lässt nur Verkehr aus den VPN-Schnittstellen zum LAN und dessen Antworten durch:
```nft
#!/usr/sbin/nft -f
flush ruleset
table inet filter {
    chain input {
        type filter hook input priority filter; policy drop;
        iif lo accept
        ct state established,related accept
        ct state invalid drop
        icmp type echo-request accept
        tcp dport 22 accept
        udp dport { 51820, 1194 } accept
    }
    chain forward {
        type filter hook forward priority filter; policy drop;
        ct state established,related accept
        iifname { "wg0", "tun0" } oifname "veth-gw" accept
    }
}
```
Die Syntax wurde mit `nft -c` geprüft (nftables 1.0.9, nicht auf Debian 12).

### Aufgabe 3 – NAT konfigurieren (Einheit 11.2)

Ergänzen Sie in `/etc/nftables.conf` die Tabelle `table ip nat` mit der Kette `postrouting` (`type nat hook postrouting priority srcnat; policy accept;`) und der Regel `ip saddr { 10.8.0.0/24, 10.9.0.0/24 } oifname "veth-gw" masquerade`. Im isolierten Labor gibt es keinen Internetausgang; die Maskierung wird daher am simulierten LAN-Host `lan-a` gezeigt. In der Praxis steht in `oifname` das WAN-Interface (Name mit `ip -br a` prüfen).

### Aufgabe 4 – Regelwerk aktivieren (Einheit 11.3)

Prüfen Sie die Datei mit `sudo nft -c -f /etc/nftables.conf` und laden Sie sie mit `sudo nft -f /etc/nftables.conf`. Prüfen Sie mit `sudo nft list ruleset`, ob die Regeln aktiv sind, und öffnen Sie von `VM 2` eine neue SSH-Verbindung (`ssh labadmin@10.0.0.1`). Als Ersatzzugang dient die Hyper-V-Konsole von `VM 1`; mit `sudo nft flush ruleset` heben Sie die Regeln im Notfall auf. Aktivieren Sie den Dienst `nftables` nicht für den Autostart.

**Hinweis/Ergänzung der Ausarbeitung:** Die Regel für SSH (`tcp dport 22`) und die Ersatzzugänge wurden nicht getestet, weil in der Testumgebung kein SSH lief.

### Aufgabe 5 – WireGuard unter Schutz testen (Einheit 11.2, Einheit 11.3)

Starten Sie `wg-quick up wg0` auf beiden VMs (OpenVPN läuft nicht). Pingen Sie von `VM 2` die Adressen `192.168.10.1` (Eingabekette) und `192.168.10.10` (Weiterleitung). Beobachten Sie auf `VM 1` mit `sudo ip netns exec lan-a tcpdump -i veth-host -n icmp`, dass der Host die Pakete von `192.168.10.1` (maskiert) und nicht von `10.8.0.100` sieht. Stoppen Sie danach `wg0` auf beiden VMs.

### Aufgabe 6 – OpenVPN unter Schutz testen (Einheit 11.2, Einheit 11.3)

Starten Sie `systemctl start openvpn-server@server` auf `VM 1` und `sudo openvpn --config /etc/openvpn/client/client1.ovpn` auf `VM 2`. Wiederholen Sie die Pings aus Aufgabe 5 und die Beobachtung mit `tcpdump`. Beenden Sie den Client (Strg+C) und den Dienst (`systemctl stop openvpn-server@server`).

## Hinweise

- Mit `policy drop` auf `input` sperrt man sich aus, wenn die Regeln für SSH und `established` fehlen. Ersatzzugang: die Hyper-V-Konsole; `nft flush ruleset` hebt die Regeln auf.
- `nft -c -f` prüft nur die Syntax; die Wirkung der Regeln zeigt erst das Laden und der Test.
- Der Dienst `nftables` wird nicht für den Autostart aktiviert.
- Die Maskierung wird im Labor am Rechner `lan-a` gezeigt, weil es keinen Internetausgang gibt; in der Praxis steht in `oifname` das WAN-Interface.

## Kontrollfragen

1. Warum ist `masquerade` (Source NAT) erforderlich, wenn VPN-Clients über das Gateway ins Internet surfen sollen?
2. Was passiert mit einer bestehenden SSH-Sitzung, wenn Sie in `nftables` die Input-Policy auf `drop` setzen, ohne vorher eine Regel für `state established` oder `tcp dport 22` anzulegen?
3. Welche Kette (Chain) in der Tabelle `filter` ist zuständig für Pakete, die von der VPN-Schnittstelle in die LAN-Schnittstelle geroutet werden sollen?

**Fragen.** (1) Clients im VPN haben private Adressen, die im Internet nicht geroutet werden. Ohne Source NAT fänden Antworten nicht zurück. `masquerade` ersetzt die Quelladresse durch die des Gateways (im Labor `192.168.10.1`). (2) Mit `policy drop` und ohne Regel für `established` oder `tcp dport 22` würden alle weiteren Pakete der Sitzung verworfen: die SSH-Sitzung hängt und bricht nach der Zeitüberschreitung ab. (Fachwissen, nicht getestet; im Lehrplan ist `ct state established,related accept` deshalb Teil des Regelwerks.) (3) Die Kette `forward` (Hook `forward`) in `table inet filter`.

## Erweiterungen

- Ergänze eine Regel `log prefix "drop: "` am Ende der `input`-Kette und lies die Meldungen mit `journalctl -k`.
