## Lernziele

Nach dieser Übung kannst du

- eine einfache Certificate Authority (CA) mit EasyRSA initialisieren
- Server- und Client-Zertifikate generieren und signieren

## Voraussetzungen

- Modul 2 (installierte Pakete, Prüfpunkt `M2-fertig`)

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **CA** | Certificate Authority: stellt Zertifikate aus und beglaubigt sie mit ihrem privaten Schlüssel |
| **PKI** | Public-Key-Infrastruktur: CA, Zertifikate, Schlüssel und Anforderungen |
| **CSR / `.req`** | Zertifikatsanforderung; wird von der CA signiert |
| **CN** | Common Name im Zertifikat; bei OpenVPN der Name des Clients |
| **`nopass`** | privater Schlüssel ohne Passphrase |
| **DH-Parameter** | Parameter für den Diffie-Hellman-Schlüsselaustausch |
| **`tun` / `tap`** | virtuelle Netzwerkgeräte: Layer 3 bzw. Layer 2 |

## Laborumgebung

| Was | Rolle in Modul 06 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |
| Verzeichnis | `/etc/openvpn/easy-rsa` auf VM 1 (CA liegt der Einfachheit halber auf VM 1, in der Praxis auf einem geschützten System) |

## Aufgabe

### Aufgabe 1 – Zustand herstellen und EasyRSA initialisieren (Einheit 6.1, Einheit 6.2)

Stoppen Sie WireGuard auf beiden VMs (`wg-quick down wg0`; läuft das Interface nicht mehr, ist die Meldung zu ignorieren). Wechseln Sie auf `VM 1` mit `sudo -i` zu root, erstellen Sie das Verzeichnis `/etc/openvpn/easy-rsa` und wechseln Sie hinein. Kopieren Sie die EasyRSA-Vorlagen dorthin (`cp -r /usr/share/easy-rsa/* .`). Führen Sie `./easyrsa init-pki` aus.

### Aufgabe 2 – CA erstellen (Einheit 6.3)

Bauen Sie die Certificate Authority mit `./easyrsa build-ca nopass` (Common Name: `VPN-Lab-CA`).

### Aufgabe 3 – Server-Zertifikat (Einheit 6.3)

Generieren Sie das Server-Zertifikat und den Schlüssel mit `./easyrsa gen-req server nopass` und signieren Sie es mit `./easyrsa sign-req server server` (Rückfrage mit `yes` bestätigen).

### Aufgabe 4 – Diffie-Hellman Parameter (Einheit 6.3)

Generieren Sie die DH-Parameter mittels `./easyrsa gen-dh`.

### Aufgabe 5 – Client-Zertifikat (Einheit 6.3)

Generieren Sie für `VM 2` (Common Name: `client1`) die Anforderung mit `./easyrsa gen-req client1 nopass` und signieren Sie sie mit `./easyrsa sign-req client client1` (Typ `client`, nicht `server`).

### Aufgabe 6 – Ergebnis prüfen (Einheit 6.2, Einheit 6.3)

Listen Sie mit `find pki -type f` die erzeugten Dateien. Erwartet werden unter `pki/` unter anderem `ca.crt`, `dh.pem`, `issued/server.crt`, `issued/client1.crt`, `private/server.key` und `private/client1.key`. Prüfen Sie mit `openssl x509 -in pki/issued/client1.crt -noout -subject -issuer`, dass der Aussteller `VPN-Lab-CA` ist.

## Hinweise

- EasyRSA aus dem Debian-Paket kann sich von der Version der Testumgebung (3.1.7, Ubuntu) unterscheiden; Ausgaben und Rückfragen können abweichen.
- Der Typ beim Signieren entscheidet über die Verwendung: `server` für den Server, `client` für den Client. Ein mit Typ `server` signiertes Client-Zertifikat hätte falsche Erweiterungen.
- Der private CA-Schlüssel `pki/private/ca.key` verlässt das System nicht; hier mit `nopass` (nur im Labor).
- Die Gültigkeit der Zertifikate in der Testumgebung: 825 Tage (EasyRSA-Voreinstellung 3.1.7).

## Kontrollfragen

1. Welchen kryptografischen Zweck erfüllen die Diffie-Hellman-Parameter (DH) beim TLS-Verbindungsaufbau von OpenVPN?
2. Warum ist der Common Name (CN) eines Zertifikats für das spätere OpenVPN-Routing wichtig?
3. Worin liegt das Sicherheitsrisiko, wenn man den Parameter `nopass` beim Erstellen der CA verwendet?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Zustand herstellen und EasyRSA initialisieren).**

```bash
sudo -i
wg-quick down wg0 || true
mkdir -p /etc/openvpn/easy-rsa && cd /etc/openvpn/easy-rsa
cp -r /usr/share/easy-rsa/* .
./easyrsa init-pki
```

Zielzustand: `Your newly created PKI dir is: /etc/openvpn/easy-rsa/pki`. In der Testumgebung wurde `easyrsa` aus dem Ubuntu-Paket benutzt (Pfade in der Ausgabe ersetzt); der Debian-Pfad `/usr/share/easy-rsa` ist **nicht bestätigt**.

**Aufgabe 2 (CA erstellen).**

```bash
./easyrsa build-ca nopass     # Common Name: VPN-Lab-CA
```

Ausgabe (Auszug, `beispiele/m06.txt`): `CA creation complete. Your new CA certificate is at: …/pki/ca.crt`. Die Rückfragen wurden in der Testumgebung automatisch beantwortet.

**Aufgabe 3 (Server-Zertifikat).**

```bash
./easyrsa gen-req server nopass
./easyrsa sign-req server server      # yes
```

Ausgabe: `req: …/reqs/server.req`, `key: …/private/server.key`, `Certificate created at: …/issued/server.crt`; Gültigkeit laut Ausgabe `825 days`.

**Aufgabe 4 (Diffie-Hellman Parameter).**

```bash
./easyrsa gen-dh
```

Ausgabe: `DH parameters of size 2048 created at: …/pki/dh.pem`; Dauer in der Testumgebung rund 15 Sekunden (hängt von der Hardware ab).

**Aufgabe 5 (Client-Zertifikat).**

```bash
./easyrsa gen-req client1 nopass         # Common Name: client1
./easyrsa sign-req client client1        # Typ client, yes
```

Ausgabe: `…/issued/client1.crt`.

**Aufgabe 6 (Ergebnis prüfen).**

```bash
find pki -type f
openssl x509 -in pki/issued/client1.crt -noout -subject -issuer
```

Erwartung (Testumgebung): `ca.crt`, `dh.pem`, `issued/server.crt`, `issued/client1.crt`, `private/server.key`, `private/client1.key` u. a.; `subject=CN = client1`, `issuer=CN = VPN-Lab-CA`. Das Server-Zertifikat enthält `TLS Web Server Authentication` (`extendedKeyUsage`).

**Fragen.** (1) Die DH-Parameter definieren die Gruppe für den Diffie-Hellman-Schlüsselaustausch, mit dem beide Seiten ein gemeinsames Sitzungsgeheimnis berechnen, ohne es zu übertragen. (Der TLS-Handshake ist laut Lehrplan nicht Gegenstand.) In der Testumgebung zeigte das Log `Control Channel: TLSv1.3 … peer temporary key: 253 bits X25519`, also einen Schlüsselaustausch über eine elliptische Kurve; ob `dh.pem` dabei überhaupt benutzt wurde, ist **nicht untersucht**. (2) Der CN identifiziert den Client; OpenVPN nutzt ihn für die Zuordnung der clientspezifischen Konfiguration (`ccd`, Modul 9) und im Log (`[client1]`). (3) Wer den CA-Schlüssel ohne Passphrase kopiert, kann beliebige gültige Zertifikate ausstellen. Die Passphrase schützt gegen Diebstahl der Datei; im Labor nicht kritisch, in der Praxis nicht empfohlen. (Aussage: Fachwissen des Verfassers, nicht gegen eine Quelle geprüft.)

</details>

## Erweiterungen

- Erstelle ein Zertifikat mit anderem CN und prüfe `openssl x509 -noout -text` auf die Erweiterungen (`extendedKeyUsage`).
- Sperre ein Zertifikat mit `./easyrsa revoke client1` und erzeuge eine CRL (`gen-crl`); die Anwendung der CRL in OpenVPN folgt nicht im Lehrplan.
