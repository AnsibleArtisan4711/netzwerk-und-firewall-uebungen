## Voraussetzungen

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Inline-Profil** | `.ovpn`-Datei, in der CA, Zertifikat, Schlüssel und `tls-crypt` als Tags eingebettet sind |
| **`remote-cert-tls server`** | der Client verlangt vom Server ein Zertifikat mit Servererweiterung |
| **`client`** | Kurzform für `pull` und `tls-client`: der Client übernimmt die vom Server gesendeten Optionen |
| **`route-nopull`** | gepushte Routen und andere Optionen nicht übernehmen |
| **`PUSH_REPLY`** | Antwort des Servers mit den Optionen für den Client |

## Laborumgebung

| Was | Rolle in Modul 08 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |
| Verzeichnis | `/etc/openvpn/client/` auf VM 2 |
| Transfer | `scp` zwischen den VMs (SSH-Server vorausgesetzt) |

## Aufgabe

### Aufgabe 1 – Zertifikats-Transfer (Einheit 8.2)

Die Schlüsseldateien sind nur für root lesbar, und ein SSH-Login als root ist unter Debian meist gesperrt (nicht bestätigt). Kopieren Sie daher auf `VM 1` mit `sudo` die Dateien `pki/ca.crt`, `pki/issued/client1.crt` und `pki/private/client1.key` aus `/etc/openvpn/easy-rsa` sowie `/etc/openvpn/server/ta.key` in das Verzeichnis `/tmp/ovpn-client` und setzen Sie `sudo chown -R labadmin /tmp/ovpn-client`. Übertragen Sie es mit `scp -r /tmp/ovpn-client labadmin@10.0.0.100:/tmp/` nach `VM 2` und verschieben Sie die Dateien dort mit `sudo` nach `/etc/openvpn/client/` (`sudo chmod 600` für `client1.key` und `ta.key`). Löschen Sie danach `/tmp/ovpn-client` auf beiden VMs mit `rm -r /tmp/ovpn-client`.

### Aufgabe 2 – Profil erstellen (Inline) (Einheit 8.1, Einheit 8.2)

Erstellen Sie auf `VM 2` die Datei `/etc/openvpn/client/client1.ovpn`. Konfigurieren Sie `client`, `dev tun`, `proto udp`, `remote 10.0.0.1 1194`, `remote-cert-tls server`. Binden Sie die vier übertragenen Schlüsseldateien inline als XML-ähnliche Tags ein (`<ca>...</ca>`, `<cert>...</cert>`, `<key>...</key>`, `<tls-crypt>...</tls-crypt>`). Legen Sie eine Sicherungskopie `client1.ovpn.bak` an.

**Hinweis/Ergänzung der Ausarbeitung:** In der Testumgebung enthielt das Profil zusätzlich `nobind`; der Lehrplan nennt die Direktive nicht, das Profil funktioniert mit und ohne (ohne `nobind` wurde nicht getestet).

### Aufgabe 3 – Verbindung herstellen (Einheit 8.3)

Der Tunnel ist WireGuard-frei (`wg0` ist gestoppt). Starten Sie auf `VM 1` den Dienst (`systemctl start openvpn-server@server`, falls er nicht läuft) und auf `VM 2` den OpenVPN-Prozess im Vordergrund: `sudo openvpn --config /etc/openvpn/client/client1.ovpn`.

### Aufgabe 4 – Verifikation (Einheit 8.3)

Öffnen Sie auf `VM 2` ein zweites Terminal (zweites Konsolenfenster oder `ssh labadmin@10.0.0.100` von `VM 1` aus) und prüfen Sie das neue Interface `tun0` (`ip a`), die gepushte Route mit `ip route` (erwartet: `192.168.10.0/24` über `tun0`) und pingen Sie die Server-LAN IP `192.168.10.1`. Beenden Sie den Client danach mit Strg+C.

## Hinweise

- Das Profil enthält den privaten Schlüssel des Clients; Rechte 600, nicht weitergeben. In den Beispielausgaben dieses Moduls sind Schlüssel- und Zertifikatszeilen ausgeblendet.
- `scp`, `ssh`-Zugang von VM 1 nach VM 2 und die Rechte von `labadmin` wurden in der Testumgebung **nicht** geprüft.
- Der Client läuft im Vordergrund; zum Prüfen ein zweites Terminal öffnen.
- Nach dem Test `/tmp/ovpn-client` auf beiden VMs löschen.

## Kontrollfragen

1. Welchen großen administrativen Vorteil bieten `.ovpn` Dateien mit Inline-Zertifikaten (insbesondere für Windows/Mobile Clients)?
2. Welche Direktive in `client` sorgt dafür, dass der Client die vom Server gepushten Routen übernimmt, und womit lassen sich gepushte Optionen auf dem Client unterdrücken (`route-nopull`)?
3. Was geschieht, wenn der Parameter `remote-cert-tls server` auf dem Client vergessen wird?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Zertifikats-Transfer).** VM 1:

```bash
mkdir /tmp/ovpn-client
sudo cp /etc/openvpn/easy-rsa/pki/ca.crt /etc/openvpn/easy-rsa/pki/issued/client1.crt \
        /etc/openvpn/easy-rsa/pki/private/client1.key /etc/openvpn/server/ta.key /tmp/ovpn-client/
sudo chown -R labadmin /tmp/ovpn-client
scp -r /tmp/ovpn-client labadmin@10.0.0.100:/tmp/
rm -r /tmp/ovpn-client
```

VM 2: `sudo mv /tmp/ovpn-client/* /etc/openvpn/client/`, `sudo chmod 600 /etc/openvpn/client/client1.key /etc/openvpn/client/ta.key`, `rm -r /tmp/ovpn-client`. **Nicht ausgeführt** (kein SSH/scp in der Testumgebung; die Dateien wurden lokal kopiert).

**Aufgabe 2 (Profil erstellen (Inline)).** `/etc/openvpn/client/client1.ovpn` (Schlüsselzeilen ausgeblendet; Aufbau wie in `beispiele/m08.txt`):

```text
client
dev tun
proto udp
remote 10.0.0.1 1194
remote-cert-tls server
<ca>   … Inhalt von ca.crt …   </ca>
<cert> … Inhalt von client1.crt (nur BEGIN/END-Block) … </cert>
<key>  … Inhalt von client1.key … </key>
<tls-crypt> … Inhalt von ta.key … </tls-crypt>
```

Sicherung: `sudo cp client1.ovpn client1.ovpn.bak`. In der Testumgebung wurde das Profil mit `printf`/`cat` zusammengesetzt und erfolgreich benutzt.

**Aufgabe 3 (Verbindung herstellen).**

```bash
sudo systemctl start openvpn-server@server        # VM 1, falls nicht aktiv
sudo openvpn --config /etc/openvpn/client/client1.ovpn   # VM 2
```

Zielzustand im Log: `Initialization Sequence Completed` (Client und Server). Beobachtung im Server-Log: `VERIFY OK: depth=0, CN=client1`, `MULTI_sva: pool returned IPv4=10.9.0.2`, `Data Channel: cipher 'AES-256-GCM'`.

**Aufgabe 4 (Verifikation).** Zweites Terminal auf VM 2:

```bash
ip a show tun0
ip route
ping -c 2 192.168.10.1
```

Erwartung (Testumgebung, `beispiele/m08.txt`): `tun0` mit `10.9.0.2/24`, Route `192.168.10.0/24 via 10.9.0.1 dev tun0`, Pings ohne Verlust. Die Client-Adresse stammt aus dem Pool (hier `10.9.0.2`; ab Modul 9 fest `.50`).

**Fragen.** (1) Eine einzige Datei enthält die komplette Konfiguration einschließlich Zertifikaten; sie lässt sich einfach verteilen, importieren (Mobilgeräte, Windows-Clients) und sichern. (2) `client` (genauer: `pull`) lässt den Client die gepushten Optionen übernehmen. Mit `route-nopull` werden gepushte Routen nicht gesetzt. (Aussage: Fachwissen des Verfassers, nicht gegen eine Quelle geprüft; der Lehrplan nennt `route-nopull`, nicht getestet.) (3) Dann prüft der Client nicht, ob die Gegenstelle ein Serverzertifikat vorlegt; jeder mit einem gültigen, von derselben CA signierten Client-Zertifikat könnte sich als Server ausgeben (Man-in-the-Middle-Risiko). In der Testumgebung **nicht** ausprobiert; Aussage: Fachwissen des Verfassers, nicht gegen eine Quelle geprüft.

</details>

## Erweiterungen

- Füge `route-nopull` ein und beobachte, welche Routen fehlen.
- Setze `verb 4` im Profil und lies im Log, welche Optionen gepusht werden.
