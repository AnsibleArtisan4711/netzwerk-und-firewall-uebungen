## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **`client-config-dir` (CCD)** | Verzeichnis mit clientspezifischen Konfigurationsdateien; Dateiname = Common Name |
| **`ifconfig-push`** | weist einem Client eine feste Adresse zu |
| **`route`** | Kernel-Route auf dem Server („Ziel liegt hinter `tun0`“) |
| **`iroute`** | interne Route in OpenVPN: „dieses Netz liegt hinter diesem Client“ |
| **Common Name** | Name aus dem Zertifikat, hier `client1` |

## Laborumgebung

| Was | Rolle in Modul 09 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |
| Verzeichnis | `/etc/openvpn/server/ccd/` auf VM 1 |

## Aufgabe

### Aufgabe 1 – CCD vorbereiten (Einheit 9.1)

Erstellen Sie auf `VM 1` das Verzeichnis `/etc/openvpn/server/ccd/`. Fügen Sie der `server.conf` die Direktive `client-config-dir /etc/openvpn/server/ccd` hinzu und starten Sie den Dienst neu.

### Aufgabe 2 – Statische IP vergeben (Einheit 9.2)

Erstellen Sie im CCD-Verzeichnis eine Datei mit dem Namen `client1` (exakt der Common Name des Client-Zertifikats). Fügen Sie die Zeile `ifconfig-push 10.9.0.50 255.255.255.0` ein.

### Aufgabe 3 – Test (Einheit 9.2, Einheit 9.3)

Beenden Sie den Client auf `VM 2` (Strg+C) und verbinden Sie neu (`sudo openvpn --config /etc/openvpn/client/client1.ovpn`). Prüfen Sie mit `ip a`, ob der Client nun zuverlässig die IP `10.9.0.50` erhält. Beenden Sie den Client danach mit Strg+C.

**Hinweis/Ergänzung der Ausarbeitung:** Das Lernziel 2 des Moduls verlangt, `route` und `iroute` zu erklären, die Aufgaben dazu folgen erst in Modul 10. Formulieren Sie in einem Absatz selbst, wofür die beiden Direktiven jeweils zuständig sind, und vergleichen Sie danach mit der Musterlösung.

## Hinweise

- Der Dateiname im CCD-Verzeichnis ist **groß-/kleinschreibungsempfindlich**: `Client1` passt nicht auf den Common Name `client1` (in der Testumgebung beobachtet: der Client bekam dann `10.9.0.2` statt `10.9.0.50`).
- Die CCD-Datei wird nach meinem Kenntnisstand bei jeder Verbindung neu gelesen (nicht getestet); nach Änderung der `server.conf` den Dienst neu starten.
- Die feste Adresse muss im Subnetz `10.9.0.0/24` liegen und nicht im Pool vergeben sein (hier `.50`, der Pool beginnt bei `.2`).

## Kontrollfragen

1. Warum muss der Dateiname im `ccd`-Verzeichnis exakt mit dem Common Name (CN) des Zertifikats übereinstimmen?
2. Warum reicht ein normaler `route` Befehl im Kernel nicht aus, um ein Subnetz hinter einem spezifischen VPN-Client zu erreichen, und warum braucht OpenVPN stattdessen `iroute`?
3. Wo (in welcher Datei) wird der Parameter `ifconfig-push` definiert?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (CCD vorbereiten).**

```bash
sudo mkdir -p /etc/openvpn/server/ccd
echo 'client-config-dir /etc/openvpn/server/ccd' | sudo tee -a /etc/openvpn/server/server.conf
sudo systemctl restart openvpn-server@server
```

Zielzustand: Verzeichnis vorhanden, Direktive in der `server.conf`, Dienst läuft. In der Testumgebung wurde der Server mit relativem Pfad `ccd` gestartet (`--cd`), `systemctl` nicht ausgeführt.

**Aufgabe 2 (Statische IP vergeben).** `/etc/openvpn/server/ccd/client1`:

```text
ifconfig-push 10.9.0.50 255.255.255.0
```

Der Dateiname ist exakt der Common Name (`client1`).

**Aufgabe 3 (Test).**

```bash
sudo openvpn --config /etc/openvpn/client/client1.ovpn     # VM 2, neu starten
ip -br a show tun0                                           # tun0 UNKNOWN 10.9.0.50/24
ping -c 2 10.9.0.1
```

Erwartung bestätigt (Testumgebung, `beispiele/m09.txt`): `10.9.0.50/24`, Ping ohne Verlust; mit dem falsch geschriebenen Dateinamen `Client1` bekam der Client `10.9.0.2`.

**Erklärung `route` / `iroute`:** `route 192.168.20.0 255.255.255.0` in der `server.conf` setzt eine **Kernel-Route** auf dem Server: Pakete für das Netz gehen an `tun0`. `iroute 192.168.20.0 255.255.255.0` in der CCD-Datei des Clients teilt der **OpenVPN-Prozess** mit, dass dieses Netz hinter genau diesem Client liegt. Beides wird für Site-to-Site gebraucht (Modul 10); `iroute` allein erzeugt keine Kernel-Route.

**Fragen.** (1) OpenVPN sucht beim Verbindungsaufbau im CCD-Verzeichnis eine Datei, deren Name dem Common Name aus dem Client-Zertifikat entspricht. Gibt es keine, wird keine clientspezifische Konfiguration angewandt (Testumgebung: Client erhielt eine Adresse aus dem Pool, keine Fehlermeldung). (2) Der Kernel kennt nur Schnittstellen, nicht die einzelnen Clients hinter `tun0`. Eine Kernel-Route sagt „an `tun0`“. Welcher der vielen Clients das Paket bekommt, entscheidet die interne Routing-Tabelle von OpenVPN; die füllt `iroute`. (Das Verhalten ohne `iroute` wurde in Modul 10 bestätigt: 100 % Paketverlust.) (3) In der clientspezifischen Datei im CCD-Verzeichnis, hier `/etc/openvpn/server/ccd/client1` (nicht in der `server.conf`).

</details>
