## Lernziele

Nach dieser Übung kannst du

- einen WireGuard-Client für den Fernzugriff einrichten
- das Prinzip "AllowedIPs" gezielt für Split- und Full-Tunneling anwenden

## Voraussetzungen

- Modul 3 (laufendes `wg0` Interface auf dem Server)

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **`AllowedIPs`** | Liste von IP-Bereichen je Peer: ausgehend Routing-Entscheidung, eingehend Quelladressfilter |
| **`Endpoint`** | Adresse und Port der Gegenstelle (bei Road Warrior nur beim Client) |
| **Split Tunnel** | `AllowedIPs` nur mit Zielnetzen des Firmennetzes |
| **Full Tunnel** | `AllowedIPs = 0.0.0.0/0`: alles durch den Tunnel |
| **`latest handshake`** | Zeit seit dem letzten erfolgreichen Handshake mit dem Peer |
| **Routingtabelle 51820** | eigene Tabelle, die `wg-quick` bei `/0` in `AllowedIPs` nutzt |

## Laborumgebung

| Was | Rolle in Modul 04 |
|---|---|
| VM 1 `vpn-a` | Debian 12, WAN `10.0.0.1/24` (Adapter `eth0`, mit `ip -br a` prüfen), simuliertes LAN Site A `192.168.10.1/24` auf `dummy0`, Benutzer `labadmin` |
| VM 2 `vpn-b` | Debian 12, WAN `10.0.0.100/24`, simuliertes LAN Site B `192.168.20.1/24` auf `dummy0` |
| Netze | WireGuard `10.8.0.0/24` (Server `.1`, Client `.100`), OpenVPN `10.9.0.0/24`, Site A `192.168.10.0/24`, Site B `192.168.20.0/24`; privater vSwitch `VPN-Lab-WAN` |
| Regel | WireGuard und OpenVPN laufen **nie gleichzeitig** (Routenkonflikt in den Netzen der Standorte) |

## Aufgabe

### Aufgabe 1 – Peer am Server eintragen (Einheit 4.1, Einheit 4.2)

Ergänzen Sie auf `VM 1` in der `wg0.conf` den Block `[Peer]` für `VM 2`. Nutzen Sie den Public Key von VM 2 (`/etc/wireguard/client.pub`) und `AllowedIPs = 10.8.0.100/32`. Übernehmen Sie die Änderung mit `wg-quick down wg0` und `wg-quick up wg0`.

**Hinweis/Ergänzung der Ausarbeitung:** Mit `Endpoint` am Client und ohne `PersistentKeepalive` kennt der Server den Endpoint des Clients erst nach dem ersten Paket des Clients. Das beeinflusst die Reihenfolge der Pings (siehe Modul 5).

### Aufgabe 2 – Client-Konfiguration (Split Tunnel) (Einheit 4.2)

Erstellen Sie auf `VM 2` die `wg0.conf` (Rechte `600`). Setzen Sie im `[Interface]` den Private Key von VM 2 und die IP `10.8.0.100/24`. Fügen Sie den Server als `[Peer]` hinzu (Public Key des Servers, `Endpoint = 10.0.0.1:51820`). Setzen Sie `AllowedIPs = 10.8.0.0/24, 192.168.10.0/24`. Starten Sie das Interface mit `wg-quick up wg0`.

### Aufgabe 3 – Verbindungstest (Einheit 4.1)

Pingen Sie von `VM 2` die Tunnel-IP des Servers (`10.8.0.1`) und dessen LAN-IP (`192.168.10.1`). Prüfen Sie mit `wg` auf beiden VMs die Zeile `latest handshake` und die Zähler `transfer`.

**Hinweis/Ergänzung der Ausarbeitung:** `wg` zeigt den Endpoint und den Handshake auf dem Server erst, **nachdem** der Client Pakete geschickt hat (Beispielausgabe auf dem Server: `endpoint: 10.0.0.100:44321`, `latest handshake: 2 seconds ago`).

### Aufgabe 4 – Full Tunnel Umbau (Einheit 4.3)

Ändern Sie auf `VM 2` in der `wg0.conf` die `AllowedIPs` auf `0.0.0.0/0` und übernehmen Sie die Änderung mit `wg-quick down wg0` und `wg-quick up wg0` (eine Änderung der Datei wirkt nicht auf ein laufendes Interface). Prüfen Sie `ip rule`, `ip route show table 51820` und `ip route get 8.8.8.8`. `wg-quick` legt die Standardroute laut Handbuch in eine eigene Routingtabelle und eine Regel an, die Tabellennummer 51820 ist nicht bestätigt, und `ip route` allein zeigt sie nicht. Ein Internetzugriff ist im isolierten Labor nicht möglich. Setzen Sie die `AllowedIPs` anschließend auf den Wert aus Aufgabe 2 zurück, starten Sie das Interface neu und wiederholen Sie die Pings aus Aufgabe 3. Der Zustand nach Modul 4: `wg0` läuft auf beiden VMs.

## Hinweise

- Eine Änderung der `wg0.conf` wirkt nicht auf ein laufendes Interface: `wg-quick down wg0` und `wg-quick up wg0`.
- Bei `0.0.0.0/0` überschreibt `wg-quick` die Standardroute nicht in der Haupttabelle, sondern legt eine eigene Tabelle und Regeln an; darum zeigt `ip route` allein die Route nicht.
- Ein Full Tunnel kann den Zugriff auf die Verwaltungsverbindung abschneiden; im Labor ist die Konsole der Ersatzzugang.
- Ein Internetzugriff ist im isolierten Labor nicht möglich.

## Kontrollfragen

1. Welche zwei Funktionen übernimmt der Parameter `AllowedIPs` in WireGuard gleichzeitig?
2. Warum erfordert ein Full-Tunnel (`0.0.0.0/0`) am Server in der Regel den Einsatz von NAT (Masquerading)?
3. Welche Route wird auf dem Client automatisch gesetzt, wenn `AllowedIPs = 192.168.10.0/24` konfiguriert ist?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Peer am Server eintragen).** VM 1, `/etc/wireguard/wg0.conf`:

```ini
[Interface]
Address = 10.8.0.1/24
PrivateKey = <server.key>
ListenPort = 51820

[Peer]
PublicKey = <Inhalt von client.pub>
AllowedIPs = 10.8.0.100/32
```

Dann `wg-quick down wg0 && wg-quick up wg0`. In der Testumgebung ausgeführt.

**Aufgabe 2 (Client-Konfiguration (Split Tunnel)).** VM 2, `/etc/wireguard/wg0.conf` (Rechte 600):

```ini
[Interface]
Address = 10.8.0.100/24
PrivateKey = <client.key>

[Peer]
PublicKey = <Inhalt von server.pub>
Endpoint = 10.0.0.1:51820
AllowedIPs = 10.8.0.0/24, 192.168.10.0/24
```

`wg-quick up wg0`. Zielzustand (Testumgebung, VM 2): `ip route` zeigt `10.8.0.0/24 dev wg0` und `192.168.10.0/24 dev wg0 scope link`, siehe `beispiele/m04.txt`.

**Aufgabe 3 (Verbindungstest).**

```bash
ping -c 2 10.8.0.1
ping -c 2 192.168.10.1
sudo wg
```

Erwartung: beide Pings ohne Verlust (Testumgebung: `0% packet loss`). `wg` zeigt auf dem Server `endpoint: 10.0.0.100:<Port>`, `allowed ips: 10.8.0.100/32`, `latest handshake: … seconds ago` und `transfer: … received, … sent`; auf dem Client entsprechend `10.8.0.0/24, 192.168.10.0/24`.

**Aufgabe 4 (Full Tunnel Umbau).**

```bash
# AllowedIPs = 0.0.0.0/0 setzen
wg-quick down wg0 && wg-quick up wg0
ip rule
ip route show table 51820
ip route get 8.8.8.8
```

Beobachtung in der Testumgebung (siehe `beispiele/m04.txt`): `ip rule` zeigt `not from all fwmark 0xca6c lookup 51820` und `from all lookup main suppress_prefixlength 0`; `ip route show table 51820` zeigt `default dev wg0 scope link`; `ip route get 8.8.8.8` ergibt `8.8.8.8 dev wg0 table 51820 src 10.8.0.100`. Die Tabellennummer 51820 und das Verhalten entsprechen dem `wg-quick`-Skript (Quelle). Ein Internetzugriff war nicht möglich. Danach `AllowedIPs` zurücksetzen, Interface neu starten, Pings aus Aufgabe 3 wiederholen (Erfolg erwartet).

**Fragen.** (1) Zum einen die ausgehende Routing-Entscheidung (Pakete mit diesen Zielen gehen an diesen Peer), zum anderen die eingehende Filterung (Pakete von diesem Peer werden nur mit diesen Quelladressen akzeptiert). (2) Die Clients haben private Adressen (hier `10.8.0.100`), die im Internet nicht geroutet werden; Pakete mit privater Quelladresse würden nicht beantwortet. Das Gateway ersetzt per Masquerading die Quelladresse durch seine eigene (siehe Modul 11). (3) Eine Route `192.168.10.0/24` über die WireGuard-Schnittstelle `wg0` (`192.168.10.0/24 dev wg0 scope link`, in der Testumgebung beobachtet).

</details>
