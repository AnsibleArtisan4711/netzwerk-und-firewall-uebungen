## Lernziele

Nach dieser Übung kannst du

- typische Routingfehler erkennen (fehlende Rückroute, falscher Next Hop, deaktivierte Schnittstelle, Tippfehler in der Zielnetzadresse),
- mit `show ip route`, `show ip interface brief` und `tracert` die Stelle des Abbruchs eingrenzen,
- die Rolle der **Rückroute** erklären: Ein Ping braucht den Weg hin **und** zurück,
- Befunde protokollieren und den Soll-Zustand wiederherstellen.

## Voraussetzungen

Das Referenznetz und das Soll-Messprotokoll aus Übung 8.1. Soll-Routen: R1 `ip route 192.168.30.0 255.255.255.0 10.0.12.2`; R2 `ip route 192.168.10.0 255.255.255.0 10.0.12.1` und `ip route 192.168.20.0 255.255.255.0 10.0.12.1`.

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| Next Hop | Adresse des nächsten Routers auf dem Weg. Sie muss in einem direkt angeschlossenen Netz liegen. |
| Rückroute | Route, über die die Antwort zum Absender zurückfindet. |
| Verbundene Route (C) | Route für ein direkt angeschlossenes Netz; nur vorhanden, wenn das Interface `up/up` ist. |
| `tracert` | Zeigt Hop für Hop den Weg; der letzte antwortende Hop grenzt den Fehler ein. |

> **Merksatz:** Ein Ping scheitert auch dann, wenn nur die Antwort keinen Weg zurück findet. Prüfe immer beide Richtungen.

## Hintergrund: Wie zeigen sich Routingfehler?

1. **Fehlende Rückroute (A):** Der Ping kommt am Ziel an, die Antwort findet den Weg nicht zurück. Der Absender sieht nur „Request timed out“. Die Ursache liegt oft am **anderen** Router als der, an dem man sucht.
2. **Falscher Next Hop (B):** Die Route steht in der Tabelle, die Adresse `10.0.12.3` antwortet aber nicht. Der Router kann das Paket nicht zustellen.
3. **Schnittstelle down (C):** Mit `shutdown` verschwindet das verbundene Netz aus der Routingtabelle, alle Routen über diese Schnittstelle werden unbrauchbar. `show ip interface brief` zeigt `administratively down`.
4. **Tippfehler im Zielnetz (D):** Die Route existiert, passt aber nicht zum gesuchten Netz. `show ip route` zeigt `192.168.3.0/24` statt `192.168.30.0/24`; für das richtige Ziel gibt es keine Route.
5. **Vorgehen:** `tracert` zeigt, bis wohin Pakete kommen. Der letzte antwortende Hop und die Routingtabelle des nächsten Hops zeigen die Lücke.

## Hinweise

- Ein statischer Routeneintrag wird nur genutzt, wenn der Next Hop über ein aktives, direkt angeschlossenes Netz erreichbar ist.
- Eine falsche Route entfernst du mit `no ip route …` und denselben Parametern.
- Für die Rückrichtung: Prüfe, ob der Zielrouter eine Route zum Netz des **Absenders** hat.
- Nach jeder Änderung `show ip route` kontrollieren, bevor du erneut pingst.

## Prüfbefehle

```text
R1# show ip route
R1# show ip interface brief
R1# show running-config | include ip route
R2# show ip route
PC> tracert 192.168.30.10
```

| CLI-Befehl | Was er zeigt | GUI-Weg |
|---|---|---|
| `show ip route` | Routingtabelle mit verbundenen und statischen Routen | Werkzeug *Inspect* → *Routing Table* |
| `show ip interface brief` | Zustand der Interfaces | Router → *Config* |
| `show running-config` | Eingetragene statische Routen | Router → *Config* → *Running Config* |
| `tracert` (PC) | Hops bis zum Abbruch | – (nur CLI am PC) |

**Kontrollfragen**

1. Warum kann ein Ping scheitern, obwohl die Hinroute stimmt?
2. Woran erkennst du `shutdown` an einem Router-Interface?
3. Was zeigt `show ip route`, wenn der Next Hop nicht erreichbar ist?
4. Wie hilft `tracert` bei der Eingrenzung?
5. Wie entfernst du eine falsche statische Route?

## Musterlösung

<details>
<summary>Musterlösung anzeigen</summary>

| Störung | Ursache | Entscheidender Befehl | Behebung |
|---|---|---|---|
| A | R2 hat keine Route zu `192.168.20.0/24` | `show ip route` auf R2 | `ip route 192.168.20.0 255.255.255.0 10.0.12.1` |
| B | R1-Route zeigt auf `10.0.12.3` | `show ip route` auf R1, `ping 10.0.12.3` | falsche Route entfernen, `ip route 192.168.30.0 255.255.255.0 10.0.12.2` |
| C | `Gi0/0` auf R2 ist `administratively down` | `show ip interface brief` auf R2 | `no shutdown` |
| D | Route auf `192.168.3.0` statt `192.168.30.0` | `show ip route` auf R1 | falsche Route entfernen, richtige eintragen |

**Beobachtungen (sinngemäß, nicht bestätigt):**

- **A:** Hin- und Rückweg unterscheiden sich: PC1 → PC2 scheitert, PC0 → PC2 klappt weiter.
- **B/D:** `tracert` von PC0 endet bei R1; die Routingtabelle von R1 enthält keine passende Route bzw. eine unbrauchbare.
- **C:** Auf R1 klappt `ping 10.0.12.2` nicht; R2 zeigt die Schnittstelle als `administratively down`.

**Beispielprotokoll Störung A:**

| Nr. | Symptom | Hypothese | Test | Ergebnis | Maßnahme |
|---|---|---|---|---|---|
| A | PC1 → PC2 timeout | Hinroute | `show ip route` R1 | Route zu `192.168.30.0/24` vorhanden | – |
| A | – | Rückroute | `show ip route` R2 | keine Route zu `192.168.20.0/24` | Route ergänzt |

**Antworten auf die Kontrollfragen:**

1. Weil die Antwort eine Rückroute braucht; fehlt sie, kommt nur ein Timeout beim Absender an.
2. `show ip interface brief` zeigt `administratively down`.
3. Die Route kann zwar in der Tabelle stehen, wird aber nicht zur Zustellung genutzt (genaue Anzeige in Packet Tracer nicht bestätigt).
4. Der letzte antwortende Hop zeigt, wo der Weg endet.
5. Mit `no ip route <Netz> <Maske> <Next Hop>`.

</details>
